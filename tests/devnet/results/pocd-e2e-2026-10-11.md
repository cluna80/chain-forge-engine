## Acceptance Test #2 — Duplicate Claim Rejection ✅

```
objective     : obj-dup-test-2
task_id       : task-dup-test-2
miner         : bossking-miner
nonce         : 104560
content_hash  : de6167af27dd1e569545308668200bfe321025c729881ab3c1b58c281f26a959
result_id     : 6825eccf-486c-4209-804e-c2c8922a128f
verification  : verifier-alpha (count=1), verifier-beta (quorum_reached=true, status=accepted)

First settle attempt (operator_nonce=2):
  HTTP 409 Conflict
  {"error":"claim_already_exists",
   "claim_id":"4d067ce8ff36796a3fa90d08d6ef5aea2771107526391abb618b30142717a7ea",
   "message":"This claim was already submitted in a prior request."}

Second settle attempt (same body):
  HTTP 409 Conflict  ← deterministic claim_id prevents any duplicate submission

bossking-miner balance after both attempts: 10,000,000 uqcb  ← no double credit ✅
```

Note: The 409 fired on the first attempt because the same deterministic claim_id
(`chain_id + objective_id + task_id + reward_kind` → SHA-256) had already been
inserted by an earlier session. This confirms the idempotency key works across
scheduler restarts and session boundaries.

## Acceptance Test #3 — Unauthorized Settlement ❌ PARTIAL FAIL

```
objective     : obj-unauth-test
task_id       : task-unauth-test
miner         : bossking-miner
nonce         : 11388
content_hash  : 0e1415fdaa4003f53fadae92e45957f9f2540088d7b0c45815f987f75e4c8f92
result_id     : 91f8d344-1b07-4560-b9a7-3c2ae6cfb257
verification  : verifier-alpha + verifier-beta → quorum_reached=true

Unauthorized settle attempt (operator_address=qcb1bob, not in genesis settlement_operators):
  Scheduler response  : 201 Created  ← INCORRECT
  claim_id            : 593bd81ff5d79cef7d304bb3125927a4b95e2f6ade020ea2e151e47589ddcd03
  tx_id               : 5a7d44ab8c4093980577d2a8...

  bossking-miner balance after attempt: 10,000,000 uqcb  ← no funds moved ✅
```

### Finding

The executor correctly rejects the TX (Guard 1: `settlement_operators.contains(&tx.sender)`
returns false for qcb1bob), so **no funds moved**. However, the scheduler's
`settle_objective()` checks only for HTTP 2xx from the node's `/api/tx` endpoint.
The node returns 200 on **mempool acceptance**, not on **execution success**.
The scheduler therefore reports 201 Created even though the TX will fail at execution.

**Root cause:** `/api/tx` is a fire-and-forget submission endpoint. Execution
result is only available after block inclusion via `/api/tx/:id`.

**Fix applied (commit 9f16472):**
Option 1 implemented: `TxPrecheck` in `chain-forge-node/src/api.rs` now carries
`settlement_operators: Vec<String>` (populated from genesis at startup). A new
match arm in the `POST /api/tx` handler rejects any `ClaimResearchReward` TX
whose sender is not in that list with HTTP 400 `{"status":"rejected"}` before
the TX enters `SharedTxQueue`. The executor-level Guard 1 (lib.rs:4392) is
preserved as defense-in-depth.

**Re-run required to promote to ✅ PASS** — rebuild node on devnet machines and
repeat the Bob settle attempt; expect HTTP 400 from node and 4xx from scheduler.

## Open Issues

### Carol Empty-Signature Warning
Observed in Dave's log at height=2:
```
WARN vote rejected: invalid signature from=12D3KooW validator=qcb1carol
     height=2 round=0 reason=validator qcb1carol has a key on file but
     vote carries an empty signature
```
Quorum reached 3/4 (Alice, Bob, Dave) without Carol's vote. Requires investigation:
- Is Carol's signing key loaded correctly at startup?
- Are empty-signature votes always dropped and never counted?
- Can this path be triggered adversarially?

### P2P Startup Dependency
Machine 2 (Carol + Dave) must be running before BossKing establishes peer TCP connections. libp2p retries peer discovery automatically — no manual restart needed once Machine 2 comes up — but block production is blocked until ≥3/4 validators connected.

**Operational requirement:** `MACHINE1_IP=192.168.137.1 bash tests/devnet/run_machine2.sh` must be started before or shortly after `run_machine1.sh`.
