# FIPS 204 ML-DSA-65 backend (`fips204` 0.5.0), isolated and inactive (DRAFT)

Stacked on PR #95 (K1 conformance and evaluation). Adds an **off-by-default** feature `fips204-backend` to `chain-forge-crypto` with a new module `fips204_backend`. **Nothing calls it.** The legacy `MlDsaScheme` (`pqcrypto-dilithium`), all existing verification paths, consensus, genesis, wallets, signing domains and state roots are unchanged; no activation, no caller switched. Not merged.

## What it provides

`chain_forge_crypto::fips204_backend::MlDsa65Fips204` (associated functions on a unit type), standard FIPS 204 **pure** ML-DSA with a context string:

| Function | Behavior |
|---|---|
| `keygen_from_seed(&[u8;32]) -> KeyPair` | FIPS 204 `KeyGen_internal`; 1,952-byte public key, 4,032-byte expanded secret key |
| `generate() -> ([u8;32], KeyPair)` | OS-RNG seed (via `getrandom`) and its key pair; store the 32-byte seed rather than the expanded key |
| `sign(sk, message, ctx)` | **hedged** signing (fresh OS-RNG randomness), the production path |
| `sign_with_randomness(sk, message, ctx, rnd)` | explicit randomness; `[0;32]` is the FIPS 204 deterministic variant. **Known-answer and reproducible test vectors only** |
| `verify(pk, message, signature, ctx)` | `Ok(())` or a specific `Error`; every failure is an `Err` |
| `validate_keypair(pk, sk)` | rejects a pk that does not belong to the sk, a malformed sk encoding, an inconsistent `rho`/`tr`, and a failing sign/verify self-test; never panics |

Strictness (each tested): keys and signatures must have **exactly** the FIPS 204 lengths (nothing truncated or padded, unlike the legacy wrapper); a context over 255 bytes is an error for signing and verification; a secret key with an invalid encoding is an `Err`, never a panic and never a signature. It is deliberately **not** a `SignatureScheme` implementation: that trait has no context parameter and a silent default context would defeat domain separation.

## Evidence (Linux sandbox; Windows pending)

New tests `chain-forge-crypto/tests/fips204_backend.rs` (16), written first; **failing before:** the test file did not compile because the module did not exist (`unresolved import chain_forge_crypto::fips204_backend`, saved in the PR). **After:** 16 passed, 0 failed:
- NIST ACVP through this backend's API: keyGen 25/25; pure-interface sigGen deterministic **byte-for-byte 15/15** (contexts up to 255 bytes); pure-interface sigVer **15/15 including the 12 NIST rejections**.
- **Signing-v2 vectors (PR #94, 29 cases):** all 29 verify or fail as recorded, and this backend **reproduces all 15 valid signatures byte for byte** from the recorded seeds (the vectors were produced by an independent Python implementation).
- Hedged signing: two signatures over the same input differ and both verify; explicit randomness is reproducible.
- Strict lengths for public key, signature and secret key; trailing bytes are rejected (the legacy wrapper accepts a 1,953-byte key).
- Context limit 255/256; wrong message, wrong context, wrong key, bit flips across the signature, constant signatures all rejected.
- Legacy comparison (feature `real-pqc`): signatures from the legacy library are **not** accepted; key pairs generated by the legacy library are valid under this backend and sign/verify (existing keys carry over).
- Regression: `chain-forge-crypto` default features 32 passed; `--features real-all` 47 passed plus the K1 suite 11 passed / 3 ignored, unchanged.
- Mutation checks on the new module (9): 7 caught (context limit, public-key truncation, signature truncation, verify always-true, self-test removed, hedging replaced by a fixed seed, fixed seed in `generate`). **2 survived**: removing the `rho` comparison or the `tr` comparison alone is still caught by the other checks and the sign/verify self-test, so those two checks are redundant by design (cheap early rejection and defence in depth), not untested behavior.

## Findings made while building it

1. **`fips204` 0.5.0 `get_public_key()` panics on an inconsistent secret key** (an internal `assert_eq!` in `private_to_public_key`, seen with an all-zero key). A caller must not use it to validate untrusted keys; `validate_keypair` therefore uses rho/tr comparison plus a sign/verify self-test. Under a build with `panic = "abort"` (an open roadmap question) that call would abort the process.
2. A **well-formed but inconsistent secret key still signs** (all-zero key, wrong `tr`), in `fips204` as in every candidate; FIPS 204 does not require a consistency check. Load secret keys through `validate_keypair`, or store the 32-byte seed and re-derive.
3. `KeyPair` (existing type) has no `PartialEq`; left unchanged.

## Not done (by design)

No caller switched; no legacy verification change; no `SchemeId`; no feature enabled by default; no wallet, consensus, genesis, signing-domain, state-root or Chain Forge change. Secrets are plain `Vec<u8>` in the returned `KeyPair`; the `fips204` key objects zeroize on drop, copies held by callers are theirs to wipe. The default-RNG signing path (`sign`) is exercised only for randomness and verification, not for constant-time or fault resistance claims.
